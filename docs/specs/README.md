# SDD 方針

仕様駆動開発では、範囲、独立レビュー、人による承認、完了を証跡で確認できるようにする。
固定長表示の挙動、デスクトップ版と Web 版の互換性、[アーキテクチャ](architecture.md)を守る。
この文書では状態遷移と承認を定める。検証と証跡の扱いは各方針を参照する。

## 方針の読み方と索引

担当する作業に必要な方針とロールの規定を読む。編集やステージの前に、権限、承認の経緯、
正確な対象パス、依存条件を確認する。

- 本則は[状態遷移と承認](#状態遷移と承認)、[引き継ぎ記録](#引き継ぎ記録)、
  [対象機能の選択](#対象機能の選択)、[文書の役割](#文書の役割)を参照する。
- 検証は[変更の種類ごとの検証](validation.md#変更の種類ごとの検証)、
  [決定的な失敗の修正ループ](validation.md#決定的な失敗の修正ループ)、
  [Qlty の証跡形式](validation.md#qlty-の証跡形式)を参照する。
- 証跡は[識別情報と必須項目](evidence.md#識別情報と必須項目)、
  [証跡の有効性](evidence.md#証跡の有効性)、[再検証の振り返り](evidence.md#再検証の振り返り)を参照する。
- 設計は[設計の責務と境界](#設計の責務と境界)、[アーキテクチャ](architecture.md#設計の責務と境界)、
  [恒久ユースケース](../requirements/use-cases/README.md)を参照する。
- 終了時は[機能の完了条件](#機能の完了条件)、[機能の終了判定](#機能の終了判定)、
  [恒久文書の更新条件](#恒久文書の更新条件)を参照する。

### ロールの手順

権限、入力、手順、結果、停止条件は [Codex のロール定義](../../.codex/agents)に従う。
指定のモデル、推論設定、サンドボックスを使い、利用できない設定があれば委任前に Main に伝える。
担当の振り分けと承認後のコミット操作は Main が担う。明示的な委任を受けた
`approval-committer` は、指定された1件のコミット操作を行える。
人による承認を代行すること、担当範囲を広げること、他のロールへ再委任することは認めない。

## 自明な変更の条件

実行時の挙動、テスト、検証要件、生成物、設定、互換性、恒久文書の役割、
ロールの契約のすべてに影響しない場合に限り、正式な機能受付を省略できる。
誤字修正や意味を変えないリンクの修正が該当する。判断に迷う変更は機能受付に回す。

## 状態遷移と承認

専用の機能ブランチを使う。受付で想定する挙動と範囲を記録し、
計画で独立にレビューできるスライスに分ける。計画の独立レビューを受けてから、
範囲を明示して人の計画承認を得て、計画だけをコミットする。
各スライスは、承認後に実装と検証を行い、独立レビュー、明示的な完了承認、
完了コミット、PR の公開の順に進める。

レビューの指摘は Main を経由して作成者に返す。承認範囲で解決できる決定的な失敗には
[決定的な失敗の修正ループ](validation.md#決定的な失敗の修正ループ)を使う。
範囲、契約、設計、依存関係、互換性、検証、重要な影響、承認境界の新たな判断には、
再計画と改めてのレビュー・承認が必要。完了済みのスライスと、影響を受けないスライスの承認記録は維持する。

全スライスをコミットし公開したら、機能の終了判定で統合後の準備状況を確かめる。
終了差分に変更があれば独立レビューを受ける。明示的な終了承認を得てから終了コミットを作り、
統合の前に別途マージ承認を得る。

### GitHub 標準のスタック PR

スライスの完了コミット直後に、対応する PR を公開または更新する。
最下位の PR の対象は `main`。後続の PR は先行 PR のブランチを対象とし、自分の層の差分だけを含める。
最上位のヘッドに全スライスと終了差分を含める。現在のリポジトリルールに従い、
GitHub 標準のスタック操作を使う。参照は `TASKS.md` に残す。
独自の台帳、統合用ブランチ、統合専用 PR は設けない。

後続ブランチを作る前、または後続作業を始める前に、先行 PR の最新ヘッドを確認する。
Verify と CodeQL、リポジトリルールで必須のその他のチェック、適用される Cloud の
チェックが、そのヘッドに対して通っていることを確かめる。
CodeQL が解析したリビジョンと、先行 PR のヘッドとの対応を記録する。
実行中、未取得、失敗、古い結果があれば後続に進まない。想定どおりのスキップは、
該当ルールが認める場合に限って通過として扱う。
終了コミットで最上位のヘッドが変わったら、影響を受けるチェックの証跡を確認し直す。

機能全体が準備でき、明示的なマージ承認を得るまで、下位の PR は開いたままにする。
Main は現在のスタックと承認済みの識別情報を確認し、リポジトリルールが許可する標準操作を使う。
すべての層で実際のマージ結果と取り込み先のコミットを確認した時点で、機能の完了とする。
一部だけの統合は未完了として記録し、マージ対象の識別情報が変わったら承認を取り直す。

### ライフサイクル状態

機能とスライスのライフサイクル状態は `TASKS.md` に記録する。
レビュー判定、承認、コミットの識別情報は状態遷移の根拠とする。
Main は、対応するロールの結果、人の明示的な承認、コミット、確認済みのマージに基づいて状態を進める。
作業が止まった場合は確認できた最後の状態を維持し、不足する事実を記録する。

計画レビューの指摘は `PLANNED` のまま `planner` に返す。承認範囲内の実装の指摘は、
`IMPLEMENTED` のまま `implementer` に返して修正を待つ。終了差分の指摘は
`feature-closer` に返す。重要な判断が必要な場合に限り、影響を受ける計画を
`PLANNED` に戻して再計画する。`SLICE_COMMITTED` はその層のコミットと PR 公開、
`CLOSED` は機能の統合完了を表す。

### 引き継ぎ記録

各ロールは次の形式で Main に返す。次の判断に必要な、ロール固有の見解、修正できる指摘、
不足する判断、重要なリスクを添える。

```yaml
feature: 対象機能のフォルダー
slice: 該当する場合は対象スライス
state_transition: 開始時の状態から証跡のある作業後の状態へ
result: 判定または完了した作業
evidence_refs: 正確な識別情報と参照できる証跡
changed_paths: 編集が許可された場合は変更した正確なパス
```

該当する計画、層のベースとヘッド、差分または終了差分の識別情報を添える。
PR があれば参照を添える。コミットの引き継ぎには実行者、コミットの識別情報、
ステージ済み差分のチェック結果を含める。Main は入力が同じ証跡を作り直さず、既存の記録を渡す。

### 人による承認

対象機能の `TASKS.md` に、承認段階ごとの状態 `Pending` または `Approved`、承認結果、
正確な範囲とパス、対応するレビューとコミットへの参照を記録する。
承認済みの状態には実際の人の承認が必要。承認者のメッセージは引用せず、結果を記録する。

計画承認は `PLAN_READY` の後に得る。レビューを受けた計画と、列挙した実装範囲に限って適用する。
完了承認は `SLICE_READY`、終了承認は `CLOSE_READY` と必要な終了差分レビューの後に得る。
マージ承認では PR の順序、取り込み先、ベースとヘッドの識別情報、マージ方式、終了コミット、
最新のチェックを特定する。機能フォルダーを削除した後も、PR か保持する終了証跡にマージ承認を残す。

### 実装変更の開始条件

実行時コード、テスト、生成物、設定の編集には、スライスの承認と計画のコミットが必要。
承認前に、製品と検証支援の正確な対象パスを列挙する。フィクスチャ、スナップショット、生成物も含める。
想定する挙動、互換性リスク、関連するテスト、検証方法、判断に影響する選択肢を示す。
一覧の外での作業や境界の重要な変更は、編集前に Main に戻す。
調査と、受付・計画文書の作成は各ロールの権限内であれば実装の承認前に行える。

### 承認後のコミット方針

承認後のコミットは Main が実行する。委任する場合は、担当の `approval-committer` を1名指定する。
計画や再計画には独立レビューの Ready と計画承認、完了には実装の独立レビューの Ready と完了承認、
終了には機能の終了判定の Close、必要な終了差分レビュー、終了承認が必要。

レビューした正確な内容、承認、対象パス、有効な必須検証、ステージ済みの差分が一致することを確かめる。
無関係な変更がないインデックスに承認済みのパスだけをステージし、ステージ済みの差分を検査する。
無関係な変更、失効した証跡、承認の不足、レビュー後の実質的な差分があれば止める。
承認などの追記はレビュー済みの製品差分と分け、証跡方針に従って検証する。
対象を絞ったコミットの識別情報、実行者、証跡を記録する。
修正が必要な場合も、過去のコミットとレビューの経緯を残す。公開とマージは別の操作とする。

## 証跡の再利用

識別情報、有効性、再利用は[証跡の取り扱い](evidence.md#証跡の取り扱い)に従う。
各承認段階の参照と現時点の判断は `TASKS.md` に置く。

## 設計の責務と境界

重要な判断について、計画、実装、レビューで[設計の責務と境界](architecture.md#設計の責務と境界)を
記録する。直接と間接の影響、責務の担当、契約と依存関係、影響を受ける挙動とテストを特定する。
レビューでは、各境界を設けるだけの理由があるか判断する。自動検査で確認できるのは、
検査に列挙されたルールまで。担当、契約、依存、採用する機能、影響範囲、検証、リスク、
承認境界が変わる場合は Main に戻して再計画する。

## 利用者向け変更の記録

利用者が確認できる挙動や互換性が変わったら `CHANGELOG.md` を更新する。
挙動を変えた場合は、該当する恒久ユースケースも更新する。
リポジトリ方針、作業の順序、実装の詳細はユースケースと分ける。
具体例が挙動を明確にする場合はシナリオを使い、未解決のリスクには担当者を決める。

## 対象機能の選択

`docs/specs/features/<feature>/` の下から1件を選ぶ。利用者が選んだ機能、
ブランチで追加・変更した機能が1件に定まる場合はその機能、目的が一意に分かる場合はその目的から決める。
指定されたベースか、既定ブランチとのマージベースと比較する。
フォルダーの存在や状態だけでは対象を決められない。機能やベースが曖昧なら Main と確認する。
再計画やブランチの変更で切り替える場合を除き、実装から機能の終了判定まで対象を維持する。

## 文書の役割

- `SPECS.md` に目的、要件、決定事項、互換性、受け入れ条件を置く。
- `TASKS.md` にスライス計画、現在の状態、承認、リスク、証跡の参照を置く。
- `TRACEABILITY.md` は、必要な場合に要件とユースケースをスライスや検証に対応付ける。
- `architecture.md` に恒久的な層の境界と依存ルールを置く。
- `docs/requirements/use-cases/` に利用者が確認できる恒久的な挙動を置く。
- `AGENTS.md` にリポジトリの制約と Main の担当の振り分けを置く。
- ルートの `README.md` に製品の概要と開発者向けの入口を置く。
- `CHANGELOG.md` にリリースごとの外部から確認できる変更を置く。

[機能テンプレート](features/_templates)を使う。`TASKS.md` では作業概要と現在の状態を先頭近くに置く。
既存の文書で作業を調整し、要件との対応や検証結果が変わったら対応表を更新する。
機能の別コンテキスト文書や、進行中の機能の別索引は設けない。

## 機能の完了条件

必要な挙動、検証、要件との対応、互換性、運用に出せる状態を確認する。
承認とコミットの各段階を終え、再利用できる知識を恒久文書に反映する。
残るリスクには担当者を定め、利用者向け文書と変更履歴への影響を確認する。
GitHub 標準のスタック全体について、実際のマージ結果を確認する。

### 機能の終了判定

`feature-closer` は統合後の受け入れ条件、承認段階の証跡、運用に出せる状態、
恒久文書の変更、リスクを確認する。判定は Close、Do not close、Human decision needed のいずれか。
Close は終了の準備とマージ前の確認に進める状態を指す。

最上位層で終了時の差分をレビューし、検証する。恒久文書に反映する変更と、
削除する対象機能文書の正確なパスを含める。
証跡は削除対象のフォルダー外に置く。無関係な機能や引き継いだ機能は残す。
承認された削除は、そのコミットを担当する1名が行う。
承認段階とマージの結果は参照できる終了証跡に残す。
すべての層が統合されたことを確認してから `CLOSED` を記録する。

### 恒久文書の更新条件

再利用する内容を、必要な箇所だけ更新する。恒久文書には現行の挙動、設計、方針を書く。
ブランチの状態、一時的な調査、解決済みの指摘、実装の経緯は、必要な間だけ対象機能の記録に残す。
