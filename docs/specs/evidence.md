# SDD の証跡方針

この文書では証跡の作成、識別、有効性、再利用を定める。
ライフサイクルの判断は[本則](README.md#状態遷移と承認)、
必要な検証範囲と Qlty の形式は[検証方針](validation.md)に従う。

## 証跡の取り扱い

判断の索引は `TASKS.md` に置く。詳細な実行記録、ログ、SARIF の全出力、ファイル一覧は、
検査対象の外にある参照可能な成果物や別ファイルに保存し、対象スライスから参照する。
機能の終了判定まで各承認段階の記録を残し、必要な証跡を保持する終了証跡に移す。

- 受付・計画担当は、調査で確認した事実と変更した文書の検証結果を記録する。
- 実装担当は、対象スライスの基準と最終の検証を記録する。
- 独立レビュー担当は、指摘、判定、レビューした内容の識別情報を記録する。
- 機能の終了判定担当は、統合と終了の証跡を記録する。

証跡を受け取る側には、必要な識別情報、判定、失敗理由、対象パス、指摘、参照先を渡す。
具体的な事実が必要なときに詳細を開く。参照できない成果物を通過の根拠には使わない。

### 識別情報と必須項目

証跡ごとに作成者、記録の版、機能とスライス、正確なベースと最終入力、承認パス、
検査パス、改名、未追跡の変更を記録する。作業ツリーには、再現できるファイル内容の一覧を使う。
設定と依存の識別情報、必須コマンド、検証範囲、ツールのバージョン、結果、生の出力の参照先を含める。
承認を受けて省いた項目や不足する事実を記録する。範囲外の入力や別の変更が混在していれば明記する。
検証に使った生成物のうち、結果に関係するものを残す。

該当する VS Code の対応範囲やホストの変更、import と export、影響を受ける層、要件との対応、
アーキテクチャテストの結果を記録する。設計の責務と境界（Solution Shape）の判断は分けて記録する。
Qlty の証跡には[品質条件](validation.md#品質条件)が定める識別情報、一覧、成果物をすべて含める。

GitHub 標準のスタックでは、PR の URL と順序、取り込み先の主ブランチ、先行層の正確な
ベースとヘッド、層の差分、統合した最上位ヘッド、終了コミット、GitHub のルールと最新ヘッドの
チェック、実際のマージの識別情報を保持する。人の承認とレビューは別々に記録する。

### 証跡の有効性

検査した内容、関連ツールや依存のバージョン、設定、承認済みの検証範囲、比較ベース、
必須コマンドの変更で、無効になった結果だけを更新する。
チェックが入力を変えた場合も、影響を受ける結果は失効する。
作業段階、レビュー担当、承認の変更や、検証済みの内容を新しいコミットと結び付けるだけなら、
入力が同じローカルの結果は有効。

Git の SHA とローカルで検証した内容の識別情報は分ける。
SHA が変わっても、内容、入力、検証範囲が一致する場合に限り、決定的な検証結果を再利用できる。
比較ベースが変わったら、そのベースに依存する結果は失効する。
GitHub と Cloud の必須チェックは PR の最新ヘッドと、必須の場合はマージグループのリビジョンに結び付く。
過去の SHA の結果は現在の必須チェックに使えない。
意味のある変更に対するレビューの有効性は[独立レビュー](validation.md#独立レビュー)に従う。

承認、状態、証跡の追記は別に検証するメタデータとし、正確な差分と範囲を残す。
挙動、リスク、承認範囲、検証コマンド、受け入れ条件の変更は実質的な変更として扱う。
解析は実際に検査した変更されない入力と結び付け、メタデータを検査対象外とした場合は明記する。
レビューと承認の対象は、実質的な差分と、別に検証したメタデータの両方。

証跡の更新を求めるのは、事実が不足している、識別情報が一致しない、指摘の再現が必要な場合に限る。
理由を記録し、影響を受けたチェックだけを実行し直す。書き込みと整形は作成者が担当する。
コミット担当はステージ済みの内容を確認し、製品の検証が失効していれば Main に戻す。

### 再検証の振り返り

不要な再検証、委任、レビューを調べるときは、既存のログと引き継ぎを使う。
影響を受ける識別情報、理由、結果は既存の証跡に記録する。
比較では範囲、リスク、設定をそろえる。測れなかった値は不明として扱う。
通常の承認段階に別の計測作業は設けない。
