# ファイル形式別エンコーディング制御とバイト長対応の仕様

## 目的

ファイル形式に応じた文字コードで文書を読み込み、固定長項目とレコードの長さを
バイト単位で評価する。表示位置は VS Code の UTF-16 座標へ変換し、未保存の編集を保護する。

## 根拠

- 2026年11月12日の依頼で、参照会話「リポジトリ改善整理」の最新候補を対象に選んだ。
  参照会話 ID は `6af1d6fa-197c-83e8-9924-2d808ff017bb`。
  最低対応版を VS Code 1.100 に変更する前提を引き継ぐ。
- ベースは `main` の `0b4400e45a9d97d86ab17658bedd593e9e95ef80`。
  現行の項目表示とレコード検証は UTF-16 単位であり、形式定義に文字コードと長さの単位はない。
- [VS Code 1.100 の公式リリースノート](https://code.visualstudio.com/updates/v1_100#_text-encodings)と
  [1.100.0 の公式型定義](https://github.com/microsoft/vscode/blob/1.100.0/src/vscode-dts/vscode.d.ts)で、
  `TextDocument.encoding` と文字コード指定の読込・変換 API を確認した。
  参照会話のコード例は実装契約とせず、実際の型定義を使う。
- 関連する恒久要件は[項目表示](../../../requirements/use-cases/uc-display-fixed-width.md)、
  [検証](../../../requirements/use-cases/uc-validate-fixed-width.md)、
  [エディター切替](../../../requirements/use-cases/uc-switch-editors.md)。

## 要件と受け入れ条件

- R1: 最低対応を VS Code 1.100.0 とする。製品の対応宣言、型定義、ロックファイル、
  最低版の検証条件を一致させ、デスクトップ版と Web 版を維持する。
- R2: 形式ごとに `encoding` と `length_unit` を扱う。`length_unit` は `utf16` または
  `byte` とし、省略時は従来の `utf16`。`encoding` 省略時は現在の文書の文字コードを使う。
  既存の `fields`、`columns`、行判定、モード切替と形式 ID の契約を維持する。
- R3: 形式選択を始めた文書 URI を保持する。指定文字コードが現在と同じなら再読込しない。
  異なり、未保存の編集がなければ標準 API で再読込する。未保存の編集がある場合は
  再読込せず通知する。拡張から文書の書換、自動保存、編集の破棄を行わない。
- R4: 読込失敗、未対応の文字コード、適用した文字コードの不一致を正常扱いしない。
  誤った前提の装飾や診断を残さず利用者に通知する。失敗時はその URI の形式選択を解除し、再選択を案内する。
- R5: 非同期処理中の別文書への切替、同一文書の再選択、編集、終了によって、古い結果を
  新しい選択や別 URI に反映しない。同じ URI の分割表示には同一の解析結果を反映する。
- R6: `byte` の形式では項目の論理位置と UTF-16 表示位置を分ける。
  Shift_JIS の全角文字、UTF-8 の日本語、サロゲートペアを含む行について、
  境界線、交互色、区切り記号、ホバー、カーソル位置の項目強調を正しい文字位置へ適用する。
- R7: バイト境界が文字の途中にある項目は、その不正な範囲を装飾せず診断する。
  行末を超える定義、短い行、長い行でも有効な UTF-16 範囲を使う。
  ホバーと診断には長さの単位が分かる情報を表示する。
- R8: レコード長と項目の範囲を選択した単位で評価する。数値型の ASCII 数字・全 ASCII SP の
  許容、診断上限、検証設定、空行の扱いを維持する。改行やファイル先頭の BOM を
  レコードの項目幅として数えない。編集、保存、文字コード変更後は最新の内容で再評価する。
- R9: 全銀33形式と JPX の既存サンプル、装飾解除、モード、エディター切替、診断の
  ライフサイクルを回帰検証する。組み込み形式の `encoding` と `byte` への移行は
  後述の一次仕様に基づき `shiftjis` / `byte` に移行する。
- R10: 文書の内容、パス、認証情報、文字変換の失敗内容をテレメトリに追加しない。
  既存のイベント一覧とオプトアウトを維持する。

## 決定事項と影響

- 利用者の成果は「形式に応じた読込とバイト長による表示・検証」で一体であるため、
  この1件の機能として受け付ける。スライスの分割と実装順序は計画担当が決める。
- 固定長のルールは VS Code に依存させない。文字コード API の呼出しと
  UTF-16 座標への変換の責務は[アーキテクチャ](../../architecture.md)に従って計画する。
  参照会話の `ByteOffsetMapper` という名前や層配置を採用済みとは扱わない。
- バイト長は選択した文字コードによる現在の文書の再エンコードを基準とする。
  元ファイルのバイト列との完全一致を保証する機能は含めない。
  変換不能文字、置換、BOM、サロゲート、対応文字コードの契約は次節に定める。
- 公式 API は未対応の文字コードを既定値へフォールバックし得る。
  例外発生だけを未対応判定に使わない。1.100.0 の `workspace.encode` は
  `workspace.encode(text, { encoding })` の形式であり、参照会話の3引数形式は使わない。
- 恒久ユースケースでは従来の UTF-16 前提と読込・エディター切替の説明を更新する必要がある。
  最低対応版の説明、利用者向け変更履歴、必要なアーキテクチャの記載も計画の対象とする。
  受付では恒久文書を変更しない。

## 互換性

最低対応版の引上げは今回の明示された変更であり、1.100 未満への対応は終了する。
単位や文字コードを省略した定義では従来の解釈を維持する。
デスクトップ版と Web 版で同じ固定長ルールを使い、Node 専用の処理を共通本番コードに入れない。

## 対象外

- EBCDIC、任意の独自文字コード、文字コードの自動推測精度の改善。
- 原本のバイト列の厳密な復元・検証、ファイルの変換保存、内容の補正。
- 利用者が定義ファイルを追加する新しい UI、業務値や必須項目の追加検証。

## 文字コードとバイト位置の契約

- `byte` の対応文字コードは `utf8`、`utf8bom`、`utf16le`、`utf16be`、`shiftjis`。
  形式の明示指定にもこの集合を使い、未知の名前や別表記を暗黙に正規化しない。
  `utf16` 単位で `encoding` を省略した従来の定義は、他の文書文字コードでも利用できる。
- バイト数は現在の文書を指定文字コードで再エンコードしたデータ部分の長さ。
  現在の行を LF で連結したスナップショットの先頭に ASCII `A` を付け、
  `workspace.encode` と `workspace.decode` を全量に各1回使って完全一致を確認する。
  先頭の `A` の直後を最初の行のバイト位置0とし、生成された BOM と補助文字を数えない。
  文書内容として存在する先頭・途中の U+FEFF は `A` の後にあるため保持して数える。
- 同じバイト列を標準 `TextDecoder` のストリーミング復号で走査し、復号された文字列を
  補助文字付きの元文字列と完全照合する。対応ラベルは順に `utf-8`、`utf-8`、
  `utf-16le`、`utf-16be`、`shift_jis`。エラーを置換するモードは使わない。
  文字が完成した境界だけを記録し、サロゲートペアの途中を境界にしない。
  改行の後で行内バイト位置を0に戻す。行末のバイト数に改行は含めない。
- VS Code の変換と標準デコーダーの不一致、往復で変化する文字、孤立サロゲート、
  変換の失敗は文書全体の解析を中止する。内容や例外を引用しない固定の通知を出し、
  その URI の形式選択、装飾、診断を消す。入力の U+FFFD だけを理由に失敗とはしない。
- 項目には定義上の開始・終了・幅と単位を保持し、表示には別の UTF-16 範囲を使う。
  `utf16` の既存ホバーの位置・桁数表記を保ち、`byte` は位置と幅にバイト単位を示す。
  短い行の項目は存在する文字まで表示し、論理幅は縮めない。行末を超える定義の
  終端線は描かない。行末から始まる項目や文字のない項目は装飾しない。
- 項目の開始または終了が実在文字の途中なら、その項目は装飾・ホバー・強調と N 型検証を
  行わず、`INVALID_BYTE_BOUNDARY` を診断する。文字途中である境界を含む文字全体を
  UTF-16 範囲にする。有効な他の項目、行判定、後続行のモード、行長検証は続ける。
- レコード長は実際の行内バイト数と定義上の終端で比較する。短い行は末尾の文字全体、
  長い行は期待終端から余分な末尾を示す。期待終端が文字途中ならその文字の先頭から示す。
  空の範囲が必要なときは行内の0幅にする。N 型は両端が有効で項目全体が存在するときだけ
  元の文字列から検証する。従来の ASCII 数字・全 ASCII SP の許容を維持する。
- `validationEnabled=false` は境界の問題を含む診断を消す。安全でない項目を描画しない規則は
  無効化しない。境界問題も従来の1000件上限に含め、上限後も表示とモード解析を続ける。

## 読込と非同期処理の契約

- コマンド開始時の文書オブジェクトと URI を保持する。選択肢を閉じた時点のアクティブ文書へ
  付け替えない。キャンセルは現在の形式と表示を保つ。開始時に文書がなければ適用しない。
- 決定した選択を処理するとき、その URI の古い描画と診断を先に消す。明示文字コードと
  現在の文字コードが異なる場合だけ `workspace.openTextDocument(uri, { encoding })` を呼ぶ。
  dirty、untitled、閉じた文書では異文字コードの再読込を行わず通知する。
  保存可能な FileSystemProvider の URI も標準 API に任せ、失敗は安全に処理する。
- 再読込前と後で、要求の世代、拡張の生存、文書の同一性、文字コードを確認する。
  同じ URI の再読込は直列化し、待機中に古くなった要求は呼出し前に捨てる。
  既に開始したホスト API の中断は保証しないが、古い完了で選択や表示を確定しない。
- 選択成功後に URI の形式を保持する。失敗時は旧形式も含め解除し、再選択で復帰する。
  解除選択は待機中の処理を失効させ、再読込しない。キャンセルは解除として扱わない。
- 解析は文書の版、文字コード、選択・描画の世代を持つ不変スナップショットを使う。
  完了時に全て一致し、同じ URI が表示中の場合だけ各エディターと診断へ適用する。
  編集、設定変更、保存、文字コード変更、終了、非表示、破棄で古い処理を失効させる。
  最新の表示が必要なら再スケジュールし、古い解析が最新の診断を消すことも防ぐ。
- 文字コード変更は `contentChanges` が空でも検出する。明示された文字コードから利用者が
  変更した場合、自動で戻さず選択・装飾・診断を解除して再選択を案内する。
  encoding 省略の `byte` 定義は現在の対応文字コードで再解析し、非対応なら安全に停止する。
- `ext.activate`、`ext.decorate`、`ext.deactivate` と既存のプロパティを維持する。
  正常な選択、開始時にエディターがない選択、キャンセルの既存通知を維持する。
  新しい読込・変換失敗の選択は空の `file_type` とし、成功した形式 ID を送らない。
  編集、再描画、古い非同期完了は追加のイベントを送らない。SDK とオプトアウトは変更しない。

## 組み込み定義の移行

- 全銀33形式の全てに `encoding: "shiftjis"`、`length_unit: "byte"` を設定する。
  [全銀協 AP-I-13](https://www.zenginkyo.or.jp/fileadmin/res/abstract/efforts/system/jba_protocol_pc.pdf)
  第Ⅰ部 §7 と付録1（印刷 pp.12、175）は、先頭のデータ区分を1バイト、使用文字を
  JIS または EBCDIC のコード表で定める。今回は JIS 系の ASCII・半角カナを扱うため、
  VS Code の `shiftjis` を使う。全銀仕様の全ての文字コードを実装したとは説明しない。
  EBCDIC は読込・変換の対象外で、コード区分の自動判別や業務文字集合の追加検証も行わない。
- JPX 四本値（デリバティブ）も `shiftjis` / `byte` にする。
  [JPX 総研データフィードサービス仕様書 v4.0](https://www.jpx.co.jp/markets/paid-info-equities/reference/co3pgt0000004g0w-att/JPXReferenceDFS.zip)
  §3.3（PDF6頁、印刷p.4）は ShiftJIS、657バイト、固定長・項目区切りなしと定める。
- 項目、行条件、モード、形式 ID と順序は変更しない。解除形式は属性を追加しない。
  文書の行ごとに解析する契約を維持し、改行のないストリームを657バイトずつ分割する機能は含めない。
  既存の ASCII サンプルは変更せず、同じ内容・範囲・診断になることを確認する。
