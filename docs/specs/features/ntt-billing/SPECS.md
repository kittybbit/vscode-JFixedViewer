# NTTの請求データの固定長形式の仕様

## 目的

NTT が公開する請求帳票の固定長ファイルを組み込み形式として選択し、
項目名、バイト境界、検証結果を確認できるようにする。
2026年9月以降の帳票を扱い、東西で共通のレイアウトは同じ定義を使う。

## 根拠と対象

- ユーザーの範囲指定に基づき、ダイヤル通話料金明細内訳書、電話番号別明細内訳書、
  電話番号別明細内訳書（ひかり電話）、専用線番号別明細内訳書の4帳票を扱う。
  各帳票を1スライスとし、同じ帳票の請求区分をそのスライスで確認する。
- 西日本の公式比較表の変更後の欄にある全項目と、東日本の対応する比較表を照合して定義する。
  [NTT西日本の新旧比較資料](https://www.ntt-west.co.jp/denwa/2026bill/meisai/charcode/)、
  [NTT東日本の新旧比較資料](https://flets.com/2026billing/moji_code.html)
- 2026年9月のリニューアル後に提供する BOM 付き UTF-8 データを対象とする。
  西日本の比較表には旧予定の「2026年1月ご請求分以降」が残っている。
  延期時に公開済み仕様を維持する説明があるため、版名には実施時期の2026年9月を使い、
  出典にある見出しの違いを案内する。
  [NTT西日本の変更案内](https://www.ntt-west.co.jp/denwa/2026bill/meisai/charcode/)、
  [延期時の説明](https://www.ntt-west.co.jp/denwa/2026bill/faq/)
- ユーザーの指定に基づき、対応版は2026年9月以降に限定する。
- [項目表示](../../../requirements/use-cases/uc-display-fixed-width.md)と
  [レコード検証](../../../requirements/use-cases/uc-validate-fixed-width.md)の共通契約を使う。

## 開発用エージェントのモデル

S1 の最初に、`feature-author`、`planner`、`plan-reviewer`、
`implementation-reviewer` のモデルを GPT-6.2 Sol へ変更する。
OpenAI の公式表記と設定値 `gpt-6.2-sol` を採用する。
この設定を使う新しいロール起動で読み込まれ、実行環境で利用できることを確認する。
[公式モデル一覧](https://learn.chatgpt.com/docs/models)、
[公式カスタムエージェントの設定例](https://learn.chatgpt.com/docs/agent-configuration/subagents)

- R0 対象4ロールの `model` だけを `gpt-6.1-sol` から `gpt-6.2-sol` へ変更する。
  `medium`、名前、説明、権限、sandbox の記述と担当を維持する。
  他3ロールの Luna 設定、グローバル設定、ロールの承認フローも維持する。
- 設定の構文と差分、7ロールの契約、実際のロール読込、対象モデルの可用性を検証する。
  既存セッションが持つ古いロール定義を設定反映の証拠に使わない。
  起動で選ばれたモデルとフォールバックの有無を記録する。
- 検証対象はこのデスクトップ環境と CLI。公式の CLI 最低版は `0.166.0`、
  調査時のローカル CLI は `0.169.0`。
  [モデルの対応クライアント](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex)

## 帳票と対応区分

<!-- markdownlint-disable MD013 -->

| 帳票                               | 対応する請求区分                   | レコード長 |
| ---------------------------------- | ---------------------------------- | ---------- |
| ダイヤル通話料金明細内訳書         | 一括請求、広域一括請求・統合請求等 | 128バイト  |
| 電話番号別明細内訳書               | 一括請求、広域一括請求・統合請求等 | 512バイト  |
| 電話番号別明細内訳書（ひかり電話） | 広域一括請求・統合請求等           | 512バイト  |
| 専用線番号別明細内訳書             | 広域一括請求・統合請求等           | 700バイト  |

<!-- markdownlint-enable MD013 -->

- 4帳票4形式を用意する。グループ識別子を `ntt`、名前を `NTT` とする。
  西日本の金沢向けは東日本の札幌サービスサポートC向けの区分と対応する。
  西日本の金沢以外は東日本の札幌サービスサポートC以外の一括請求の区分と対応する。
- ダイヤルと固定電話は両請求区分で項目配置が共通であり、それぞれ1形式にまとめる。
  ファイル名のお客様番号10桁・12桁と、データ内の12バイト欄への先頭 SP 補充を認める。
  表示名に東西の会社名や問い合わせ先ごとの重複を作らず、利用案内で対象区分を説明する。
- 表示名は `NTT/ダイヤル通話料金明細内訳書（2026年9月以降）` のように帳票と版を示す。
- 全形式を `encoding: utf8bom`、`length_unit: byte` とする。
  手動選択の既存経路で再読込する。

## 項目表示と検証

- 定義は静的 JSON で表し、既存ローダー、行条件、モード、バイト位置変換を使う。
  全レコードを公式表の順序と位置に照合する。初回と継続行を通番などの条件で区別する。
  行の正規表現で参照する位置より前の文字が ASCII であることを確認し、
  バイト位置と UTF-16 位置の混同を防ぐ。
- 公式表の「文字」を `C`、数字だけの「数字」を `N` とする。日時やコードの文字型を保つ。
  固定幅の繰返し内訳は項目ごとに展開し、繰返し番号から同名項目を識別できる名前にする。
  金額の暗黙小数点は桁を保つ。仕様注記で先頭の半角マイナス等を認める欄は、
  `符号付き数値` など許容値を表す型表示にし、既存の `N` 診断を適用しない。
  正当な負値に誤診断が出ないことを検証し、型表示と公式注記の対応を証跡に残す。
- 全種別と継続行を含む架空サンプルをレイアウトごとに用意する。
  ダイヤルは ASCII 値、他3帳票は仕様上の日本語欄に架空文字を含む UTF-8 を使う。
  欄の終端は文字の途中に置かず、予備と固定幅の余白は SP で埋める。
- サンプルは CRLF と末尾 CRLF、ファイルの先頭だけに BOM を置く。
  ファイル名、管理レコードの識別番号・請求年月、明細と合計を整合させる。
  公式サンプルの個別値を転載しない。
- 未知種別、幅不足・超過、数値欄の不正値を既存の診断に通す。
  全 SP の数値欄は既存契約どおり許容する。文字の途中の不正バイト境界も確認する。
- 正常時の全項目、ホバー、診断0件、形式切替、文書・保存・書込みの不変を検証する。
  公式サンプルの構造・長さは照合に用い、配布サンプルは架空の値で作る。

## 設計と互換性

静的な形式の責務は Resource、JSON の登録と変換は Infrastructure が担う。
Domain の照合と位置、Application の投影と検証、Presentation の選択と描画を再利用する。
共通定義をデスクトップ版と Web 版に取り込み、最小対応版 `1.100.0`、
全銀・JPX の挙動、文書を変更しない契約、テレメトリのイベントとオプトアウトを保つ。
イベントには文書内容、パス、認証情報を含めない。

README、CHANGELOG、サンプル案内と項目表示の恒久ユースケースに対応帳票を追記する。
共通の検証ユースケースは再利用する。エンジン、依存、公開設定、CI、最小版を変える必要が
判明した場合は、実装を広げる前に Main に判断を戻す。

## 対応範囲の判断

今回の対象は2026年9月以降の公開4帳票とする。現行の公開形式で追加の根拠が得られた場合は、
Main が全項目の公式仕様と既存エンジンでの表現可否を確認し、帳票ごとのスライスを再計画する。
CSV、レコード間の業務整合性検証、コード表の全件実装、性能検証基盤は今回の範囲外。
