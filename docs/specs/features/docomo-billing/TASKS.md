## 設計の責務と境界

<!-- markdownlint-disable MD013 -->

| 担当 | 決定と維持する契約 | 確認 |
| --- | --- | --- |
| 定義リソース・インフラストラクチャ | `docomo.json` を既存ローダーに追加する。形式 ID は `M@docomo` 等、表示名は「NTTドコモ/」に仕様の明細名を続ける。既存形式の ID、表示名、並び順を保つ。 | ローダーの定義・選択肢の照合 |
| ドメイン・アプリケーション | 既存の行条件、バイト幅の項目射影、行長・境界・N 型の診断を共用する。 | 全レコードの項目と異常系のテスト |
| VS Code アダプター・プレゼンテーション | 既存の `shiftjis` アダプター、形式選択と再読込、表示・ホバー・診断を共用する。 | コマンド経路テストと両実ホストの確認 |
<!-- markdownlint-enable MD013 -->

- レコード判定は既存の正規表現を使う。管理と集計末尾の前置空白は ASCII SP、
  明細系の識別コードより前は ASCII の項目なので、正規表現で許す前方部分を1バイト文字に制限する。
  電話番号の妥当性判定は行わず、規定の空白埋めを許容する。
  種別・M の連番の判定と全行の長さの検証は既存の各段階に任せる。
- 各定義に `encoding: shiftjis`、`length_unit: byte`、第4章の `.cla` ファイル名パターンを設定する。
  ファイル名のパターンは既存と同じ定義情報として登録し、文書の形式は利用者が選択する。
- 全行で現行の行役割別配色を使う。管理は青、電話番号別の明細・内訳は橙、
  M の請求書作成番号は紫、電話番号別の合計は緑、M の合計とその他の終了は灰色。
- 仕様に ASCII 数字のみの固定桁と明記された項目には `N` を使う。
  電話番号、右詰めや左詰めで数字と空白を許す値、符号や英字を取り得る値は `C` または型なしとする。
  書式の幅や分割位置は保ち、料金や番号の業務上の妥当性判定は既存の対象外とする。
- 本番コードの追加依存はローダーから定義 JSON への import のみ。
  設定、最小 VS Code、拡張の入口と組み立て、テレメトリイベントとオプトアウトは現行契約を維持する。
  形式選択イベントは既存のプロパティに定義済みの ID を渡す。

## S1 ご利用内訳明細・通話等明細

**価値と依存。** 計画のコミット後、M（262バイト）と F（138バイト）をそれぞれ選択して使用できる。

**受け入れ条件。**

- M は管理 `01`・合計 `91` を13–14バイト目、電話番号別内訳 `11`・請求書作成番号 `51` を
  16–17バイト目で識別する。後者は18–19バイト目の `01` を初回、`02`–`99` を継続として表示する。
  `00`、数字以外、連番不足は未定義として診断する。
  3-2 と 3-3-2 にある9反復の項目をそれぞれ展開する。
- M の第1レコードは番号付きの詳細表 3-3-1 を採用する。
  口座種別（123）、口座番号（124–130）、口座名義（131–170）と氏名（176–215）の独立した項目を検証する。
- F は管理 `01`・終了 `91` を12–13バイト目、電話番号別明細 `11`・電話番号別合計 `51` を
  15–16バイト目で識別する。通話先の日本語、ハイフン編集済みの着信先電話番号、割引・分計先を確認する。
- 各レコードで全項目の開始・終了・幅と行長を独立した期待値で確認する。
  例として、電話番号に管理・終了と同じ数字が識別位置に現れても、明細の分類を維持する。
  CRLF と末尾 CRLF、空行、短い行・長い行、未知のコード、分断した2バイト文字を検査する。
  正常な半角カナ、全角文字、空白埋めと符号、`N` の許容値と不正値を区別する。
- デスクトップと Web の実ホストで各形式を確認する。未保存の編集がある場合の再読込の保護と、
  形式解除、分割表示・エディター切替、既存形式の回帰を確認する。

**計画承認の対象パス。**

- `src/resource/definitions/docomo.json`（新規）
- `src/infrastructure/definitions/loadBuiltInDefinitions.ts`
- `src/test/extension.test.ts`
- `src/test/support/docomoFixtures.ts`（新規。合成明細と定義から独立した期待値）
- `src/test/support/docomoSmoke.ts`（新規。デスクトップと Web の共有実ホスト確認）
- `src/test/smoke.ts`
- `docs/specs/features/docomo-billing/TASKS.md`（状態と証跡）

**リスクと対象外。** M の図と詳細表の不一致は[調査の証跡](#調査と計画の証跡)を参照。
この層では A、W、J、G、E を登録しない。共通の対象外は[検証と変更範囲](#検証と変更範囲)を参照。

## S2 データ・海外・Wi-Fi 通信明細

**価値と依存。** S1 の完了コミットと公開 PR の最新チェック通過後、A（156バイト）、W（128バイト）、
J（126バイト）、G（156バイト）、E（124バイト）を追加し、固定長7種を選べるようにする。

**受け入れ条件。**

- A・W・J・G は管理 `01`・終了 `91` を12–13バイト目、電話番号別明細 `11`・合計 `51` を
  15–16バイト目で判定する。E は4種類とも12–13バイト目で判定する。
- 各仕様の全項目の開始・終了・幅と行長を独立した期待値で照合し、共通の CRLF・空行・未知コード・
  長さ・バイト境界・許容値の検証を追加する。同幅の A と G も個別に選択でき、項目配置を取り違えない。
- G の原本第15版のレコード図、全種類の詳細表とファイル名を参照する。
  G と E は実ホストで CP932 の `81 7C` が U+FF0D として読め、2バイトを使うことを検証する。
  G の接続会社（国名）と E の区分、および後続項目の範囲を照合する。
  正常な空白埋め・符号・編集済み文字列に誤診断がないことを確認する。
- 両実ホストで5種類の設定と表示・診断を確かめ、M/F と他の既存形式も引き続き選択・表示できることを確認する。

**計画承認の対象パス。**

- `src/test/support/docomoFixtures.ts`
- `src/test/support/docomoSmoke.ts`
- `docs/specs/features/docomo-billing/TASKS.md`（状態と証跡）

**リスクと対象外。** Web で抽出された G の本文は一部ページが欠けるので原本の図表を目視で照合する。
S1 の形式・行定義はこの層の編集対象外。

## 検証と変更範囲

- 定義と検証用データは[仕様書](SPECS.md#根拠)の詳細表から別々に入力し、レコードごとに位置と幅を照合する。
  既存のテストデータと同様に TypeScript の合成データを使う。公式デモの値やファイルは追加しない。
  該当する型と境界の追加テストの失敗時は、まず定義とデータを照合する。
- 共通ケースは既存デスクトップテストのコマンド実行経路で確認する。実ローダーで得た選択肢を選び、
  既存ホストテスト支援を使って行名・項目名、バイト位置のホバー、実文字範囲、診断と変更保護を検査する。
- 共有実ホスト確認は `src/test/smoke.ts` から実行する。既存の NTT 実ホストテストに沿ってファイルシステム
  プロバイダーで合成 CP932 バイトを渡し、VS Code で再読込してから装飾を適用し、診断、UTF-16 範囲、
  CRLF、書き込みが発生しないことを検査する。表示されたホバーと組み込み選択は各デスクトップ安定版と
  Web 安定版でも、合成データを一時ディレクトリに書き出し、実コマンドから各形式を選んで確認する。
- 各スライスの必須コマンドは `npm ci`、`npm exec -- tsc -p . --noEmit`、
  `npm exec -- webpack --mode production --devtool false`、`npm run test:prepare`、
  `npm run test:architecture`、`npm run test:desktop`、`npm run test:desktop:min`（1.100.0）、
  `npm run test:web`（安定版 Chromium）。CI では Verify の実行環境に従う。
- [Qlty の品質条件](../../validation.md#品質条件)に従う。0.645.0 以降の同一バージョンと同一設定で、
  各層の実装前ベースと最終差分のリポジトリ全体に `qlty check --all --sarif --no-fix` と
  `qlty smells --all --sarif --no-snippets` を実行し、公式 SARIF 2.1.0、解析パス一覧と件数、
  版と設定ハッシュ、入力の識別情報、終了コードを保持する。基準と最終の両方で
  `npm run qlty` の出力と終了コードを記録し、最終の総合チェックの通過を確認する。
  基準の総合チェックは同じ基準コミットの検査用コピーで実行し、整形前の基準入力を保持する。
  最終の解析パスには新規パスを含め、指摘の新規・悪化がないことを確認する。
  整形で検証入力が変わった場合は、変更内容と識別情報を残し、影響を受ける結果を取り直す。
  対象外の整形はレビュー対象の差分に含めない。
- Markdown 変更は対象ファイルの lint、相対リンク・構造、`git diff --check` で検証する。
  ビルド・テストの生成物は既存の出力先に作成する。追跡するバイナリー、スナップショット、設定、
  新しい依存、既存定義や共通実装の変更は両スライスの対象外。
- Qlty の起動時には、書き込み可能な各検査用リポジトリのルートに `mkdir -p .qlty/logs` を実行する。
  隔離クローンでは既存の無視設定がこのディレクトリに適用され、Qlty 0.645.0 が起動した。
  起動・保存確認は `/tmp/jfixedviewer-docomo-qlty-preflight-20261122.txt` を参照する。
  予備確認では `smells` が39ファイルを解析して終了コード0、`check` が権限エラーで終了コード99となり、
  SARIF が空だった。ログと出力は起動・保存確認の記録から参照できる。
  `check` を実行できる環境は未確定。実装時は同じツール・設定・対象選択で必要な出力を取得し、
  未取得の必須検証は通過と記録しない。
  CP932 の往復や行判定に設計の変更が必要になる場合は、証跡を添えて Main に戻す。
