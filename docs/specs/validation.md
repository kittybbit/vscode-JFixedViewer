# SDD の検証方針

この文書では検証範囲、修正ループ、Qlty、独立レビューを定める。
承認とライフサイクルは[本則](README.md#状態遷移と承認)、
証跡の識別と再利用は[証跡の取り扱い](evidence.md#証跡の取り扱い)に従う。

## リスクに応じた検証

影響に応じてチェックを選ぶ。失敗時や境界での挙動、入力サイズ、互換性、ホストの挙動、
アーキテクチャ、プライバシー、依存関係、性能、利用者向け文書のうち、該当する項目を考慮する。
受付と計画では調査と文書の検証を行う。実装では承認された最終検証をすべて実施する。

### 決定的な失敗の修正ループ

`implementer` は、仕様、タスク計画、ユースケース、アーキテクチャ、受け入れ時のチェックから、
コミット済みの契約を確認し、再現する失敗の原因を調べる。
失敗したコマンド、診断、影響パスを残す。本番コード、テスト、フィクスチャ、生成物、ツールの
どこに不備があるかを特定してから変更する。

修正は明示的に承認されたパスに限る。挙動、契約、互換性、設計の責務と境界（Solution Shape）、
依存方向、検証範囲を維持する。合意済みの契約に沿って、lint、ビルド、型のエラー、
既知の依存ルール違反、誤ったテストやフィクスチャを直す。生成物を作り直す場合は、
承認済みの入力と設定を使う。期待出力の差分は、受け入れ済みの挙動と照合する。
正常系、異常系、境界、プライバシー、互換性のうち、それぞれ意味のある検証を残す。
既存の失敗、環境に依存する失敗、結果が不安定な失敗は証跡を添えて区別する。

修正に新しいパスが要る場合や、範囲、設計、契約、依存、互換性、リスク、検証、承認について
判断が要る場合は、編集前に止める。Main が再計画、独立レビュー、改めての計画承認に回す。

実装中は、失敗に最も近いチェックと関連する境界テストで修正を確かめる。
実質的な差分が固まってから、必須のビルド、ホストテスト、アーキテクチャ、Qlty を最終検証する。
試行ごとのレビューやコミットは不要。独立レビューで承認範囲内の修正を指摘されたら、
修正し、影響を受ける証跡を更新して、全差分の独立再レビューを依頼する。
判断が必要な指摘は Main に返す。

公開後に最新 PR のチェックが失敗した場合、Main は失敗の証跡とヘッドを実装担当者に返す。
決定的な失敗を直したら、影響のある範囲を検証し、独立レビューと対象を限定した完了承認を得る。
Main は同じブランチに修正だけのコミットを追加し、同じ PR を更新する。過去のコミットと無関係な
承認記録を維持する。後続に着手する前に、新しいヘッドで必須のチェックを確認する。
後続層で影響を受ける証跡とレビューは、[証跡の有効性](evidence.md#証跡の有効性)に従って更新する。

### テストの構成と修正

ユースケース、各コンポーネントの契約、アーキテクチャのルールに沿ってテストを組む。
共通の挙動は1か所で検証する。ホスト固有の互換性やアダプターの境界がある場合は、
ホスト別のテストを使い、実ホストのスモークテストを維持する。
誤ったアサーションは承認済みの契約に沿って修正する。テストや検証範囲の削除・縮小には、
その変更を対象とする承認が必要。

### 変更の種類ごとの検証

- **受付、計画、仕様。** 変更した Markdown をすべて lint し、相対リンクと構造を確認して
  `git diff --check` を実行する。要件との対応、文書の担当、ライフサイクル状態、承認の経緯を確認する。
- **SDD 方針、ロール、PR 文書。** 設定の構文を確認し、担当の振り分け、承認、修正、再計画、
  スタックの終了結果を静的なシナリオで確かめる。
- **CI、分析、設定、依存関係。** 変更した実行条件と影響を受ける製品チェックを検証し、
  変更前後の検証範囲と指摘を比較する。Qlty の入力や対象の選び方に重要な変更があれば、
  品質条件に従う。
- **製品コード。** 影響を受ける挙動とアーキテクチャ、必要なビルド、Qlty の品質条件を検証する。
  共通の挙動、依存の組み立て、ホストのアダプター、入口、その設定を変えた場合は、デスクトップ版と
  Web 版で検証する。ホスト互換性を変えた場合は、最小対応のデスクトップ版 VS Code で
  スモークテストを行う。

複数の種類に当てはまる変更では、該当する条件をすべて適用する。各チェックは
Pass、Failed、Missing、または理由付きの Not Applicable で記録する。
必須チェックの失敗や証跡不足があれば準備完了と判定しない。
適用される GitHub のルールと、最新ヘッドの必須チェックはローカルの検証とは分けて記録する。
例外の承認で必須の GitHub または Cloud チェックを回避することはできない。

### Qlty の証跡形式

#### 品質条件

Qlty は 0.645.0 以降を使う。基準と最終のスナップショットは全体を対象とし、
ツールのバージョン、設定、リポジトリ内での対象の選び方をそろえる。
各スナップショットで両コマンドの公式 SARIF 2.1.0 出力、解析パスの一覧と0件でない件数、
正確な識別情報、実際の終了コード、総合チェックの結果を保持する。

新規または悪化した SARIF の指摘が1件でもあれば、準備完了と判定しない。
パスと、対応を確実に取れる指摘を照合し、悪化する方向と重大度を考慮する。
出力の不足や形式の不備、解析の未完了、設定の不一致があれば検証を止める。
解析が完了し、指摘が原因で終了コードが0以外になった場合は、その値を残す。
ツールや実行自体の失敗とは分けて記録する。

最終の総合チェックは通過を要件とする。未変更の既存指摘だけが原因で通らない場合は、
Main が該当する指摘と承認段階を特定し、人に明示的な判断を求めることができる。
失敗した総合チェックと証跡は保持する。新規指摘、実施できない解析、必須の GitHub または
Cloud チェックの失敗は例外の対象外。スキャナーの設定を維持し、
独自の比較ツールを追加せず、公式の SARIF 記録を使う。

#### 実行手順

基準と最終のスナップショットを別々に用意し、いずれも使い捨ての環境で実行する。

```sh
qlty check --all --sarif --no-fix
qlty smells --all --sarif --no-snippets
```

バージョン、設定のハッシュ、解析パスの一覧と件数、スナップショットの識別情報、
コマンドの終了コードと生の出力を残す。使い捨ての最終スナップショットで `npm run qlty` を実行する。
承認済みパスに整形の変更があれば作業ツリーへ反映し、レビュー対象の差分が固まるまで最終検証を繰り返す。
対象外の整形は範囲の問題として扱い、差分に入れない。

### 独立レビュー

Ready と判定できるのは、対応可能な指摘がすべて解決した場合。
計画の独立レビューでは計画承認の前に、機能全体、範囲、テスト可否、着手できる状態を確認する。
実装の独立レビューでは、検証後に、その層の正確な全差分、受け入れ条件、証跡、リスクを確認する。
ホスト、アーキテクチャ、設定、挙動に関する重要な懸念から2件目のレビューを行う場合は、
理由を記録する。有効な証跡は再利用する。修正後は全差分を改めて独立にレビューする。

スタックでは、正確な先行ベースと対象層のヘッドを使う。意味のある差分が変わった場合や、
統合上の具体的な懸念がある場合は、影響を受ける範囲をレビューする。
機能の終了判定では、有効なスライスの証跡を再利用し、統合した検証範囲と、
適用される Qlty Cloud など最新ヘッドの全体チェックを確認する。
恒久文書を編集した場合は、その変更に該当する検証を行う。
